## Rationale

- **maturity: mvp** — the mechanical inference is `spike` (no CI, no SemVer tag, single
  committer), but every one of those signals is a thing a first release *creates*: the repo is
  v0 **feature-complete** (all three verbs + skill-install shipped, 214 tests, green gate green
  per `TODO.md`) and explicitly intended for distribution (family "never-source-build" policy →
  Homebrew tap + release installer). `spike` would forbid a `distribution` block and CI — the
  exact things this release must add — so `mvp` is the honest tier. **Not `production`**: that
  needs ≥2 recent committers + existing CI + a release gate, none of which hold yet. *← the
  single most important field to confirm.*
- **ecosystems: [rust]** — one Cargo workspace, two crates; no other manifests. Not `binary`
  (that is only for repos with no package ecosystem).
- **targets: crates.io ×2** — both `project-canon-core` (library keel) and `project-canon-cli`
  (the `project-canon` binary) publish to crates.io (owner-confirmed 2026-08-15). Workspace
  `repository`/`license`/`description` are all present; the bin can only publish once its `core`
  dep is published, so both are listed. Coexists with the Homebrew/binary `distribution` layer.
- **distribution: cargo-dist, shell + homebrew installers** — cross-platform prebuilt binaries
  via cargo-dist (macOS arm64/x86_64 + musl Linux arm64/x86_64 by the normalizer's default),
  attached to GitHub Releases, with a `homebrew` installer (the **primary** delivery channel —
  how the tool is installed on our machines) plus a `shell` curl installer as the mac+linux
  fallback. `homebrew_tap: jarimustonen/homebrew-project-canon` follows the family's
  one-tap-per-tool convention (cf. `homebrew-ossctl`, `homebrew-issuectl`,
  `homebrew-orchestratectl`). **Prerequisite:** that tap repo does not exist yet — it must be
  created (empty, public) before the cut, exactly like the sibling tools' taps.
- **versioning: zerover** — the repo calls itself **v0** and deliberately stays pre-1.0; both
  crates are at `0.0.0`. ZeroVer caps major at 0, so the first cut lands `0.1.0` and breaking
  changes bump the minor.
- **conventional_commits: true** — history is Conventional-Commits shaped (`feat(...)`,
  `fix(...)`, `chore(...)`, `docs(...)`), so `release plan` can derive the bump for review.
- **changelog: fragment / issuectl-trailers** — the repo is issuectl-based and its own
  `CLAUDE.md`/`AGENTS.md` reference `issuectl changelog` as the trailer-driven fragment source;
  this matches the family convention even though there is a single committer today.
- **release: gated / single** — one shared version + tag for the workspace (single layout);
  `gated` keeps the human approval boundary at cut time (never `auto`).
- **provenance_level: keyless** — binaries will be built + signed in CI (cargo-dist +
  GitHub attestations); keyless is the mvp default. `slsa-l3` is production-only.
- **dependency_bot: dependabot** — mvp+ default; none configured yet (a readiness gap `/oss-ci`
  will close).
- **health_badges: [ci, registry, license]** — CI (mvp), crates.io registry (a target exists),
  MIT license. Coverage/scorecard are production-tier.
- **license: MIT** — declared explicitly in the workspace `Cargo.toml`; kept as-is (not
  overridden to the Rust `MIT OR Apache-2.0` two-file convention — that is a maintainer choice).

## Release notes

- **This is a BOOTSTRAP, not a one-shot cut.** The OSS core is incomplete: **no CI workflow,
  no `LICENSE` file** (only the SPDX id in the manifest), **no tags**, and both crates are at
  **`0.0.0`**. `/oss-release` will refuse a cut until `/oss-ci` + `/oss-readme` (LICENSE) land
  and the core audit is clean.
- **Stale crate descriptions.** `project-canon-cli`'s manifest still says "Verbs land in later
  issues" — fix before any crates.io publish (crates.io text is public and permanent-ish).
- **Irreversibility (if crates.io targets are kept):** a crates.io publish of a
  `name@version` is **permanent** — the name is claimed forever and that exact version can
  never be re-published. Confirm the crate names and the `0.1.0` number before the cut.
- **Rollout gate (owner decision, per `TODO.md`):** cutting this **first release** is the gate
  that unblocks `homebase-canon-cutover` and the cross-repo go-wide. When the cut lands, the
  owner is to be told explicitly.
